## 结论与结果

主要机制是**提前生产crop＋有界待处理队列＋异步提交/完成交接，减少每框之间暴露出来的供给和确认等待**。不是识别框变少、计算量减少或改了精度；不把收益等同于已证明kernel并发。

同13张独立图片×普通/增强、软件解码/det N1、原FP32引擎、rec batch1。每组预热26页后正/反/正三轮78页，首尾两个同步与两个full进程都保留，以各自总时间均值比较：

| 路径 | 78页用时（秒） | 比完整4槽多用（秒） |
|---|---:|---:|
| 原同步（首尾均值） | 260.179 | 36.641 |
| 完整4槽（首尾均值） | 223.538 | 基准 |
| 4套资源，但只允许1项rec在途 | 240.133 | +16.594 |
| 提交后立刻等待对应Stream完成 | 240.062 | +16.524 |
| 每页逐框等待，不提前生产后续crop | 253.507 | **+29.969** |
| CTC移回I/O所有者内联执行 | 228.904 | +5.365 |

- 本轮聚合吞吐提升 **16.39%**，净省36.641秒。取消页内提前生产后，约29.969秒重新暴露，约相当于本轮净时间收益的**81.79%**；这是该反向干预撤销的收益比例，**不是可与其它项相加的独立贡献份额**。最强信号是“等当前crop全部消费/回收后才准备下一项”会使整体接近原同步。
- 限1项rec在途或提交后立即等待，各损失约16.5秒；说明非阻塞持续推进有额外价值，可能包含宿主准备/入队/传输/收集与GPU执行的交叠，不能全部记为kernel同时执行。主动等待Stream完成的组仍优于旧同步，不能把架构整体收益等同于GPU请求重叠。
- CTC内联损失约5.4秒，较小，但这是阻塞I/O推进的架构影响，不是“CTC算法加速了5.4秒”。原算法未变。
- 历史E164为17.71%，本轮有统一host打点且重新测量，不能精确追溯历史39.463秒的构成。首尾配对吞吐提升分别14.057%/18.732%（观测值范围，不是置信区间）；同步三轮总时间255.319→265.039秒，漂移+9.720秒；full223.852→223.225秒，漂移−0.627秒。历史与本轮同量级，不以挑选某轮来凑17.71%，也不抹去漂移。

### 哪部分时间没有减少

78页每组均3438次rec。完整4槽与逐框等待组的原rec准备线程CPU时间分别3.243/3.070秒，CTC分别5.381/5.350秒，`execute_async_v2`宿主线程CPU分别25.479/25.616秒；量级相近，后者整链路却慢29.969秒。因此证据支持改变**供给/交接和等待暴露的位置**，而不是这些函数本身突然算快了。两组方法wall也有嵌套/重叠，不能相加求总时间。

旧同步rec Session.run累计wall90.009秒/线程CPU36.247秒，内含execute_v2 wall79.317秒/CPU27.930秒。full的submit41.782秒/CPU32.681秒、collect6.910秒/CPU4.481秒；不能把90−49直接算成净提速，因为入口语义不同且GPU计算被延后等待。模型输入/原宽度/调用次数一致，软件N1统一，收益不是新量化、rec合批、缩短长行、丢框、硬解或det N2。

没有新增特权GPU时间线。旧四页profiler窗口的0重叠不代表本轮正常运行完全无kernel重叠；消融能确认架构开关的端到端影响，不能精确拆分kernel/传输/驱动内部成本，也没有实测GPU空闲比例。仅冻结13图的有限实验，无GT、稳定尾延迟、24h或实车结论。

## 预声明

同13图×普通/增强、原宽度/裁剪/字典/精度，软件解码、det N1、rec batch1、两活动页，复用E164 C++二进制和r19交付源码。每独立进程先原串行26页参考及26页串行时间，再候选完整预热26页和正/反/正三轮78页；沿用原质量/调用/宽度及资源门槛，失败不接受、不挑最快单轮。顺序预定sync→full→one_inflight→blocking_submit→no_fanout→inline_ctc→full→sync；首尾基线用于报告漂移，不拿旧机器状态当本轮基线。

| 模式 | 唯一干预（相对完整4槽） | 能回答什么 |
|---|---|---|
| sync | 原同步stage/1基线 | 本轮是否复现历史整体收益 |
| full | 原4槽stage/2 | 当前完整候选基线 |
| one_inflight | 仍分配4槽，但GPU所有者最多允许1个rec处于提交后待收集状态 | 取消多rec在途机会的端到端代价；不是物理kernel并发证明 |
| blocking_submit | 同4槽，每次det/rec提交后立即等待对应Stream完成，保留CPU队列/独立CTC | 宿主非阻塞提交的端到端价值；不改buffer/算法 |
| no_fanout | 每页生产一个crop后等其安全消费/回收再生产下一个 | 页内提前供给和跨crop流水线的价值；最多两活动页供给，不等于全部串行 |
| inline_ctc | 原CTC函数体移到I/O所有者收到resume后内联执行，保留空闲CTC线程以维持线程数 | 独立CTC完成入口的价值，包含其对I/O推进的影响，不能只叫CTC算术成本 |
